# AgencyOS implementation audit — 2026-11-11

## 1. Executive finding

**Conclusion: substantial product foundations exist, but this checkout cannot be declared traceable to an approved Master PRD, complete, production-ready, or ready for StageShow UI/UX refinement.** This is a provisional, static audit of branch `arena/311eeabb-agencyos-arena` at `846c9d8ddb0a0415e74e26ec5eb9cdbea96ab70d`. It maps all 84 rows in the checked-in RTM, but that RTM is itself unapproved and expressly says it was not machine-diffed against the original specification.

The conservative row tally is **15 Evidenced, 35 Partial, 17 Not evidenced, 1 Interface-only, 14 Deferred by the RTM, and 2 Not verifiable statically**. “Evidenced” means code appears to meet the RTM row on static inspection; it does **not** mean a test passed. Candidate unit, integration, and E2E suites are present, but none were executed for this audit.

In the audited base snapshot, the most material release concerns were that the automation HTTP event route accepted caller-controlled event data and authorized dispatch with `workflow.read`; other critical gaps included missing backup/restore evidence, invoice creation accepting arbitrary nonempty status strings, and unresolved production architecture/storage decisions. Follow-up reproduction, mitigation, and validation results from this worktree are recorded in the addendum at the end of this report. Several client-facing and cross-module requirements in the draft RTM are absent or only internally implemented.

## 5. Architectural and delivery risks

1. **Unapproved requirements/architecture baseline.** Planning status and old metadata conflict with the implemented code. A modular-monolith/event-bus design is proposed in `docs/02_ARCHITECTURE_PROPOSAL.md:13–22`; ADR-0002 describes pg-boss, while `run-workflow-service.ts:6–11` explicitly says execution is synchronous and there is no worker. Resolve the target architecture/hosting/storage/queue before treating current behavior as an approved design.
2. **Automation event authenticity and authorization boundary (base-snapshot finding; current follow-up in §10).** The original session route accepted `type`, `recordType`, `recordId`, and arbitrary `record` fields; dispatch required `workflow.read` while actions could write allowlisted same-org records. A read-only caller forging a matching event and causing a same-org task status write was reproduced with mocked persistence before the fix (no database or existing record touched). This branch keeps the public HTTP route at 410 and adds trusted server-only producers with session-derived actor/organization, resource-permission checks, organization-scoped record loading, and tenant-scoped action writes. Remaining limitations are synchronous best-effort delivery without an outbox and no ownership ACL beyond the existing resource-permission model.
3. **No durable async execution path.** Workflow rules execute synchronously and business services now emit events after successful CRM writes, but there is no worker, scheduler, delayed job, or transactional outbox. Retry reloads the current organization-scoped record for dynamic `$` action paths rather than retaining the original record snapshot; a later record edit can therefore change unresolved action targets. Process crashes or database failures can still lose events, and time-based reminders remain unsupported.
4. **Financial state integrity (provisional).** At the audited snapshot, invoice creation accepted an arbitrary string status (addressed in the follow-up addendum); this worktree restricts initial and manual update statuses, and only recorded payments may mark an invoice paid. Estimate conversion uses a total-only Estimate model and emits zero tax/no item breakdown; no source line items exist in that model, so the remaining issue is requirement fidelity, not confirmed data loss. Tax opt-in and currency-safe expense reporting still need confirmation against approved requirements and runtime tests.
5. **Public client surface is not a portal.** Shareable documents are read-only public snapshots, and internal approval APIs are not client authenticated. The checked-in UI blueprint describes a client portal and client acceptance/revision flows (`docs/03_UI_UX_BLUEPRINT.md:124–129,145–160`); these are not implemented in the audited route inventory. A link must not be represented as portal access or verified e-signature.
6. **Storage/deployment coupling and data durability.** Project uploads use local filesystem storage. No production object-store adapter, signed URLs, backup/restore job, or restore-test evidence was found. The hosting choice is open/unapproved in planning. This is a production data-loss/availability risk.
7. **Security assurance is incomplete.** MFA is absent in the inspected Better Auth config; rate limiting was not found; audit append-only and redaction are not enforced consistently; tenant isolation tests exist but were not run. Static guards reduce risk but do not demonstrate a release security posture.
8. **Admin controls can imply guarantees they do not provide.** Feature flags can be managed but no runtime gates were found. `/api/health` checks DB only, not queue/storage. Backup, retention, import/export, global search, custom fields, and developer workspace are absent in the inspected inventory.
9. **UI/NFR criteria are specified but not verified.** The UI blueprint requires reduced motion, skip link, WCAG AA, touch targets ≥44px, four states on every screen, and responsive phase reviews (`docs/03_UI_UX_BLUEPRINT.md:133–141,169–187,191–199`). Source scanning found specific gaps; there was no browser/device/a11y run.
10. **Audit coverage is bounded by stale/unapproved docs.** The RTM is not verified against the Master PRD; no line-by-line PRD diff was possible. Requirements beyond its 84 rows may be missing.

### Automation event finding

- In the audited base snapshot, the HTTP route was the only non-test call path for `dispatchWorkflowEvent`; there were no business-domain producers. The route accepted caller-supplied event type, record type/ID, record snapshot, and previous status. Dispatch authorized with `workflow.read` while the action engine could write same-organization records. Retry was scoped to the execution and rule organization but reconstructed an empty event record, so dynamic `$` action paths could not resolve.
- **Before the fix**, an isolated Vitest reproducer with mocked persistence passed: a session with only the `workflow.read` permission supplied `record.created` and a caller-controlled matching field; the dispatcher invoked `task.updateMany` for a same-organization task status write. No PostgreSQL, server, or existing record was touched. This confirms the code-path authorization defect in isolation, not its deployed exposure or severity.
- **Current worktree:** `POST /api/v1/automation/events` remains disabled (410) without parsing or dispatching the body. CRM business services for Lead, Opportunity, Project, Task, Estimate, Invoice, Proposal, and Quotation emit strict server-side references after successful writes. The producer derives actor/organization from the authenticated session, requires the source resource permission, loads the persisted row under tenant scope, and builds the event snapshot. Mutating actions independently require target-resource permissions and tenant-scoped optimistic writes; action mutations and notifications are audited. Unique execution and notification keys provide idempotency for a persisted event version (create events remain tied to immutable `createdAt`); retry uses an atomic claim, requires `workflow.execute` plus source-resource read permission, re-loads the tenant-scoped row for dynamic action paths, retains the original action definitions/event version, and records a retry audit entry.
- **Residual risks:** dispatch is synchronous and not in a transactional outbox, so a crash or database outage can lose an event; failed snapshot/authorization events are logged but do not have an execution row. Retry reloads current record values rather than an immutable original snapshot, so dynamic paths may resolve differently after later edits. There is no lease/recovery mechanism for a process crash that leaves an execution `running`. Keep the public HTTP route disabled.

### Invoice status and financial integrity

Manual update input permits only `draft`, `sent`, or `voided`; the service transition table and edit UI agree, while `paid` and `overdue` are not accepted as manual updates. Tests cover invalid states, legal/illegal transitions, organization-scoped lookup, and payment invariants.
